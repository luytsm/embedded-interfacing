# 7.5 De ideale ISR

Een ISR is een gewone functie, en technisch kan er dus eender welke code in
staan. Toch is een ISR niet de plaats om veel werk te doen. Deze sectie
overloopt waarom, en wat er wel en niet in een ISR thuishoort.

## 7.5.1 Waarom een ISR kort moet zijn

Zolang een ISR loopt, staat de rest van het programma stil:

- **`loop()` wacht.** Alle taken uit de superloop schuiven op. Een ISR die
  lang duurt, geeft dus hetzelfde probleem als een trage taak in de superloop
  (zie [7.1.3](./7.1_de_superloop.md#713-de-reactietijd-van-een-superloop)), maar dan erger: `loop()` kan er niets aan doen.
- **Andere interrupts wachten.** Een interrupt met dezelfde of een lagere
  prioriteit wordt pas afgehandeld wanneer de ISR klaar is (zie [7.2.2](./7.2_wat_is_een_interrupt.md#722-het-verloop-van-een-interrupt)).
  Treedt dezelfde interrupt ondertussen meerdere keren op, dan blijft daar
  maar één melding van over.
- **De ESP32 grijpt in.** Een *interrupt watchdog* bewaakt dat interrupts niet
  te lang de processor bezetten. Duurt een ISR te lang, dan herstart de ESP32,
  met in de Serial Monitor een `Guru Meditation Error` die naar de
  *Interrupt wdt* verwijst.

## 7.5.2 Wat niet in een ISR thuishoort

Sommige functies horen niet in een ISR, omdat ze te lang duren of omdat ze
niet vanuit een ISR opgeroepen mogen worden.

**`Serial`**

- `Serial.print()` is traag. Aan 115200 baud duurt één byte 87 µs (zie
  [5.2.8](../5_seriele_communicatie/5.2_uart.md#528-hoe-snel-is-uart)), en een regel tekst al snel een milliseconde.
- Op de ESP32 gebruikt `Serial` bovendien een **lock** van FreeRTOS. Die zorgt
  ervoor dat twee taken niet tegelijk naar dezelfde UART schrijven. Op zo'n
  lock wachten mag een ISR niet. Een `Serial.print()` in een ISR laat de ESP32
  daardoor crashen en herstarten.

**`delay()`**

- Op de ESP32 is `delay()` een oproep naar `vTaskDelay()` van FreeRTOS (zie
  [4.3.6](../4_gpio/4.3_digitale_output.md#436-onder-de-motorkap-het-esp-idf)). Die legt een **taak** te slapen, maar een ISR is geen taak. Ook
  dat laat de ESP32 crashen.
- `delayMicroseconds()` werkt wel, omdat die actief wacht, maar maakt de ISR
  net zo lang als de wachttijd.

**`millis()`**

Bij `millis()` ligt het genuanceerder:

- Op de **Arduino Nano** wordt de waarde van `millis()` bijgewerkt door een
  timer-interrupt. Die kan niet uitgevoerd worden zolang een andere ISR loopt.
  `millis()` opvragen in een ISR geeft dus het tijdstip waarop de ISR
  startte, maar de waarde loopt niet verder. Wachten tot `millis()` een
  bepaalde waarde bereikt, blijft eindeloos duren.
- Op de **ESP32** leest `millis()` rechtstreeks een hardware-timer uit, en is
  de functie gemarkeerd met `ARDUINO_ISR_ATTR`. In `cores/esp32/esp32-hal-misc.c`
  (versie 3.3.12):

  ```c
  unsigned long ARDUINO_ISR_ATTR millis() {
    return (unsigned long)(esp_timer_get_time() / 1000ULL);
  }
  ```

  `millis()` opvragen in een ISR mag dus, bijvoorbeeld om het tijdstip van een
  gebeurtenis bij te houden (zie [7.7.1](./7.7_use_cases.md#771-een-drukknop-debouncen)). Erop wachten maakt de ISR
  opnieuw te lang.

**Kommagetallen**

Op de ESP32 is rekenen met `float` in een ISR standaard **niet** toegelaten.
De toestand van de floating-point-unit hoort bij een FreeRTOS-taak, en een ISR
is geen taak. Een berekening met `float` hoort dus in `loop()`: de ISR geeft
enkel de ruwe waarde door.

*Bron: [Espressif, ESP-IDF FreeRTOS – Floating Point Usage](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/system/freertos_idf.html#floating-point-usage)*

**Alles wat wacht**

Een lus die wacht tot een pin verandert, een sensor die via I²C uitgelezen
wordt, een berekening over een hele array: dat werk hoort in `loop()`.

### Overzicht

| In een ISR                                                    | Wel | Niet |
| ------------------------------------------------------------- | :-: | :--: |
| een `int` of `bool` aanpassen: `press_count++`, `led_on = !led_on` | ✅  |      |
| `digitalRead()` en `digitalWrite()`                           | ✅  |      |
| `millis()` en `micros()` opvragen (ESP32)                     | ✅  |      |
| `Serial.print()`, `Serial.printf()`, ...                      |     | ❌   |
| `delay()`                                                     |     | ❌   |
| rekenen met `float`                                           |     | ❌   |
| wachten op een pin, een tijd of een sensor                    |     | ❌   |

`digitalRead()` en `digitalWrite()` zijn in de ESP32-core, net zoals
`millis()`, gemarkeerd met `ARDUINO_ISR_ATTR` (zie de code van
`digitalWrite()` in [2.3](../2_arduino/2.3_de_arduino_core.md)): ze zijn bedoeld om ook in een ISR te
gebruiken.

## 7.5.3 Zo kort mogelijk

Idealiter is een ISR **zo kort mogelijk**:

- **Niet te veel trachten te doen.** Wat niet tijdsgebonden is, kan nadien in
  `loop()` verwerkt worden. Tijdsgebonden is enkel wat op het moment van de
  interrupt zelf moet gebeuren: een puls tellen, een tijdstip noteren, een
  pin uitlezen voor ze terug verandert, of een uitgang meteen uitschakelen
  (zie [7.7.3](./7.7_use_cases.md#773-een-noodstop)).
- **Eén statement kan volstaan.** Een ISR met één regel code is geen
  uitzondering, maar de bedoeling.
- **Eenvoudige operatoren**, zoals:
  - een teller verhogen: `press_count++;`
  - een toestand omdraaien: `led_on = !led_on;`
  - een **vlag** zetten: `is_door_opened = true;`

Een voorbeeld: een deurcontact (een *reed switch*) dat een alarm geeft. Zo
hoort het **niet**:

```cpp
void ARDUINO_ISR_ATTR handle_door_isr() {  // WRONG: far too much work for an ISR
  Serial.println("door opened");
  digitalWrite(ALARM_LED_PIN, HIGH);
  delay(ALARM_DURATION_MS);
  digitalWrite(ALARM_LED_PIN, LOW);
}
```

Deze ISR print, en wacht met `delay()` tot de alarmled uit mag: op de ESP32
crasht ze, op een Nano houdt ze het hele programma vast. Zo wel:

```cpp
volatile bool is_door_opened = false;  // flag: set by the ISR, handled in loop()

void ARDUINO_ISR_ATTR mark_door_isr() {
  is_door_opened = true;
}
```

De ISR doet enkel het tijdsgebonden deel: noteren **dat** de deur open ging.
Het printen en het aansturen van de alarmled gebeurt in `loop()`, zonder
`delay()`. Dat principe heet werken met **vlaggen**, en is het onderwerp van
[7.6](./7.6_vlaggen.md).
