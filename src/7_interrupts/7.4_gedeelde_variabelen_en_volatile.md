# 7.4 Gedeelde variabelen en volatile

Een ISR heeft geen parameters en geen return-waarde (zie [7.3.4](./7.3_gpio_interrupts_in_de_arduino_core.md#734-een-isr-declareren)). Wil de ISR
iets doorgeven aan de rest van het programma, dan kan dat enkel via een
variabele die in de scope van beide zit, meestal een **globale variabele**.
Zo'n gedeelde variabele vraagt extra aandacht.

## 7.4.1 Het probleem: compileroptimalisaties

Een compiler probeert code zo snel mogelijk te maken. Een variabele die vaak
gelezen wordt, houdt hij bijvoorbeeld bij in een **register** van de
processor, in plaats van ze telkens opnieuw uit het geheugen te lezen. Dat
mag, zolang de compiler zeker is dat de waarde ondertussen niet verandert.

Net daar wringt het bij een interrupt. De compiler ziet nergens een oproep
naar de ISR: de hardware roept ze op, op een onvoorspelbaar moment. Voor de
compiler kan een variabele die in een stuk code nooit aangepast wordt, dus
ook niet veranderen.

Een voorbeeld: een sketch die in `setup()` wacht tot er op een startknop
gedrukt wordt.

```cpp
const int START_PIN = 25;  // D2

bool is_start_pressed = false;  // WRONG: shared with the ISR, but not volatile

void ARDUINO_ISR_ATTR mark_start_isr() {
  is_start_pressed = true;
}

void setup() {
  pinMode(START_PIN, INPUT_PULLUP);
  attachInterrupt(digitalPinToInterrupt(START_PIN), mark_start_isr, FALLING);

  while (!is_start_pressed) {
    // wait for the start button
  }
}
```

In de `while`-lus wordt `is_start_pressed` nergens aangepast. De compiler mag
de variabele dus één keer lezen, en daarna eindeloos verder rekenen met die
eerste waarde: `false`. De ISR zet de variabele in het geheugen wel op `true`,
maar de lus kijkt nooit meer naar het geheugen. De sketch blijft voor altijd
wachten.

Zo'n fout is verraderlijk, omdat ze niet altijd optreedt. Of de compiler
optimaliseert, hangt af van de omliggende code. Een variabele die in `loop()`
gelezen wordt, wordt meestal toch opnieuw uit het geheugen gehaald, omdat
`loop()` telkens opnieuw opgeroepen wordt. Een sketch kan dus perfect werken,
tot een kleine aanpassing elders de compiler een andere keuze laat maken.

## 7.4.2 Het keyword volatile

Het keyword **`volatile`** (*vluchtig*) vertelt de compiler dat een variabele
kan veranderen buiten de normale flow van het programma om (zie [A3.5.4](../appendix_3_static/appendix_3_static.md#a354-niet-te-verwarren-static-const-en-volatile)):

- elke keer dat de code de variabele leest, wordt ze opnieuw uit het geheugen
  gelezen;
- elke keer dat de code de variabele aanpast, wordt de nieuwe waarde meteen
  naar het geheugen geschreven.

De compiler past op die variabele dus geen optimalisaties meer toe die op
een vaste waarde rekenen. Daaruit volgt een eenvoudige regel:

> **Elke variabele die zowel in een ISR als in de rest van het programma
> gebruikt wordt, is `volatile`.**

Het voorbeeld uit [7.4.1](#741-het-probleem-compileroptimalisaties) werkt correct met één woord extra:

```cpp
volatile bool is_start_pressed = false;  // shared between the ISR and setup()
```

Een tweede voorbeeld: de led gaat aan zodra de knop één keer ingedrukt is.

```cpp
const int BUTTON_PIN = 25;  // D2
const int LED_PIN = 2;      // D9, built-in LED

volatile bool is_button_pressed = false;  // shared between the ISR and loop()

void ARDUINO_ISR_ATTR mark_press_isr() {
  is_button_pressed = true;
}

void setup() {
  pinMode(LED_PIN, OUTPUT);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  attachInterrupt(digitalPinToInterrupt(BUTTON_PIN), mark_press_isr, FALLING);
}

void loop() {
  digitalWrite(LED_PIN, is_button_pressed);
}
```

Eens ingedrukt, blijft de led aan: niets zet `is_button_pressed` terug op
`false`. Hoe `loop()` zo'n melding verwerkt en terugzet, komt aan bod in
[7.6](./7.6_vlaggen.md).

> **Let op:** `volatile` maakt een variabele niet constant en verandert niets
> aan de scope of de levensduur. `volatile` combineren met `static` of met
> `const` kan (zie [A3.5.4](../appendix_3_static/appendix_3_static.md#a354-niet-te-verwarren-static-const-en-volatile)).

### Ook voor de registers van een peripheral

Een interrupt is niet de enige reden voor `volatile`. Een variabele kan op
drie manieren veranderen zonder dat de code zelf iets doet:

- een **ISR** past ze aan, zoals in de voorbeelden hierboven;
- een andere **taak** past ze aan, bij een RTOS (zie [7.1.5](./7.1_de_superloop.md#715-een-alternatief-een-rtos));
- de **hardware** past ze aan.

Dat laatste geldt voor de **registers** van een peripheral. Op een
microcontroller staan die registers op een vast adres in het geheugen
(*memory-mapped*). De code leest en schrijft ze zoals een gewone variabele,
maar de peripheral kan de inhoud op elk moment zelf veranderen, en reageert
op elke schrijfopdracht.

Een voorbeeld: een peripheral met drie registers. Om een opdracht te geven,
wacht de code tot de peripheral niet meer bezig is, schrijft eerst de data,
en daarna het commando. Het schrijven van het commando start de opdracht.

```cpp
struct peripheral_t {
  int command;
  int data;
  int is_busy;
};

// WRONG: the registers are not volatile
void send_command(peripheral_t *peripheral, int command, int data) {
  while (peripheral->is_busy) {
    // wait until the peripheral is ready
  }
  peripheral->data = data;        // first the data
  peripheral->command = command;  // writing the command starts the action
}
```

Zonder `volatile` loopt dit op twee manieren fout:

- **De wachtlus**: de compiler leest `is_busy` één keer, en rekent daarna
  verder met die waarde, zoals in [7.4.1](#741-het-probleem-compileroptimalisaties). Was de peripheral bezig, dan
  blijft de lus eindeloos wachten.
- **De volgorde**: voor gewone variabelen maakt het voor het programma niet
  uit in welke volgorde `data` en `command` geschreven worden. De compiler mag
  de twee opdrachten dus omwisselen. Voor de peripheral maakt dat wel uit: komt
  het commando eerst, dan start de opdracht met de vorige data.

De oplossing is opnieuw één woord: de pointer wijst naar een `volatile`
struct.

```cpp
void send_command(volatile peripheral_t *peripheral, int command, int data) {
```

De compiler moet zich dan houden aan wat er staat: `is_busy` wordt bij elke
doorloop van de lus opnieuw gelezen, elke schrijfopdracht wordt effectief
uitgevoerd, en de volgorde van de toegangen blijft dezelfde.

Zelf zo'n struct schrijven is zelden nodig: de fabrikant declareert de
registers al als `volatile`.

- In de AVR-core schrijft `digitalWrite()` naar het `PORT`-register via een
  `volatile uint8_t *out` (zie [2.3](../2_arduino/2.3_de_arduino_core.md#ter-vergelijking-digitalwrite-in-de-avr-core)).
- In het ESP-IDF zijn de registers van de GPIO-peripheral één grote
  `volatile` struct: in `components/soc/esp32/register/soc/gpio_struct.h`
  begint ze met `typedef volatile struct gpio_dev_s {`.

*Bron: gebaseerd op een antwoord op [Stack Overflow, Why is volatile needed in C?](https://stackoverflow.com/a/246148)*

## 7.4.3 volatile is niet genoeg

`volatile` zorgt ervoor dat elke toegang tot een variabele effectief naar het
geheugen gaat. Het zorgt er **niet** voor dat die toegang in één keer gebeurt.
Een interrupt kan tussen twee machine-instructies vallen, ook midden in één
regel C-code (zie [7.2.2](./7.2_wat_is_een_interrupt.md#722-het-verloop-van-een-interrupt)). Dat geeft problemen in twee situaties.

### Een waarde lezen in meerdere stappen

Op een Arduino Nano is een `int` 2 bytes groot (zie [3.2.1](../3_c_en_cpp/3.2_datatypes.md#321-de-basistypes)). De
ATmega328P is een 8-bit-processor: een `int` lezen gebeurt in twee stappen,
één byte per keer. Valt de ISR tussen die twee stappen, dan krijgt `loop()`
een mengeling van de oude en de nieuwe waarde:

- `press_count` is 255 (`0x00FF`), en `loop()` leest het lage byte: `0xFF`;
- de ISR verhoogt `press_count` naar 256 (`0x0100`);
- `loop()` leest het hoge byte, dat nu `0x01` is;
- resultaat: `0x01FF`, of 511.

Op de ESP32 is een `int` 4 bytes groot, en leest de 32-bit-processor die in
één instructie. Daar treedt dit probleem voor een `int` of een `bool` niet op.

### Lezen, aanpassen en terugschrijven

Een opdracht zoals `press_count--` of `press_count = press_count - 1` bestaat
altijd uit drie stappen: lezen, aanpassen, terugschrijven. Dat geldt ook op
de ESP32. Stel dat `loop()` telkens één druk verwerkt, en de teller daarna met
1 verlaagt:

1. `loop()` leest `press_count`: 3.
2. De ISR verhoogt `press_count` naar 4.
3. `loop()` schrijft 3 − 1 = 2 terug.

De druk uit stap 2 is verloren gegaan: de teller had 3 moeten zijn.

### Vuistregels

Met twee vuistregels zijn deze problemen meestal te vermijden:

1. **Laat één kant schrijven.** De ISR past de variabele aan, `loop()` leest
   ze enkel. Wat `loop()` al verwerkt heeft, houdt ze bij in een eigen
   variabele (zie de encoder in [7.7.2](./7.7_use_cases.md#772-een-rotary-encoder-met-interrupts)).
2. **Lees een gedeelde variabele één keer**, in een lokale kopie, en werk
   verder met die kopie. Zo blijft de waarde binnen één doorloop van `loop()`
   dezelfde.

Moeten beide kanten toch schrijven, dan moet de interrupt tijdens die
toegang even tegengehouden worden. Dat valt buiten dit vak: in de voorbeelden
van deze cursus volstaan de twee vuistregels.
