# 5.5 Serial in de Arduino core

In [2.2](../2_arduino/2.2_de_serial_monitor.md) kwamen de basisfuncties van de Serial Monitor al aan bod. Deze sectie
gaat dieper in op het `Serial`-object: waar het vandaan komt, welke functies
er zijn, welke functies het programma laten wachten, en hoe een tweede UART
gebruikt wordt voor een externe module.

## 5.5.1 Waarvoor wordt de seriële poort gebruikt?

In de praktijk zijn er drie toepassingen:

- **Debuggen**: veruit de belangrijkste. Waarden van variabelen uitprinten,
  en zien welke delen van de code uitgevoerd worden (zie [2.2](../2_arduino/2.2_de_serial_monitor.md)). Op de ESP32
  komt daar logging bij (zie [2.3.2](../2_arduino/2.3_de_arduino_core.md#232-onder-de-motorkap-digitalwrite-in-de-esp32-core)).
- **Input vragen aan de gebruiker**: commando's of instellingen ingeven via
  de Serial Monitor, zonder dat er al knoppen of een display nodig zijn.
- **Een peripheral uitlezen of aansturen**: een GPS-module, een
  fijnstofsensor, een RS-485-transceiver (zie [5.3](./5.3_rs232_rs422_rs485.md)) of een ander board.

De eerste twee gebruiken UART0, de verbinding met de computer (zie [5.4.4](./5.4_van_usb_naar_uart.md#544-de-uarts-van-de-esp32)).
Voor de derde wordt meestal een tweede UART gebruikt (zie [5.5.5](#555-een-tweede-uart-gebruiken)).

## 5.5.2 Het Serial-object

`Serial` is een **object** van de klasse `HardwareSerial`. Elk object stuurt
één UART aan. De core maakt dat object zelf aan, daarom werkt
`Serial.begin()` zonder dat `Serial` ergens gedeclareerd moet worden.

- In de **ESP32-core** zijn er drie objecten: `Serial0`, `Serial1` en
  `Serial2`, voor UART0 tot UART2. `Serial` is een andere naam voor
  `Serial0` (zie de opmerking in [5.4.4](./5.4_van_usb_naar_uart.md#544-de-uarts-van-de-esp32)).
- In de **AVR-core** (Arduino Nano) is er enkel `Serial`: de ATmega328P heeft
  maar één UART.

`HardwareSerial` is afgeleid van de klasse `Stream`, en die op haar beurt van
`Print`. Alle functies van `Stream` en `Print`, zoals `print()` en
`readString()`, zijn daardoor ook beschikbaar op `Serial`.

### Waar staat de documentatie?

Het referentiepunt is de officiële
[Arduino-documentatie over Serial](https://docs.arduino.cc/language-reference/en/functions/communication/serial/).
Die is geschreven voor de AVR-core. De ESP32-core is een andere core (zie [2.3](../2_arduino/2.3_de_arduino_core.md))
en heeft geen eigen API-referentie voor `Serial`. Wie wil weten wat een functie
op de ESP32 precies doet, of welke extra functies er zijn, kijkt dus in de
broncode: `cores/esp32/HardwareSerial.h` in de map van de core (zie [2.3.2](../2_arduino/2.3_de_arduino_core.md#232-onder-de-motorkap-digitalwrite-in-de-esp32-core)).

De functies op een rij:

| Functie                                | Doet                                                         | Wacht?                     |
| -------------------------------------- | ------------------------------------------------------------ | -------------------------- |
| `begin()`, `end()`                     | start of stopt de UART                                       | nee                        |
| `available()`                          | geeft het aantal ontvangen bytes in de ontvangstbuffer       | nee                        |
| `read()`                               | haalt één byte uit de buffer, of geeft `-1` als die leeg is  | nee                        |
| `peek()`                               | bekijkt de volgende byte, zonder ze uit de buffer te halen   | nee                        |
| `print()`, `println()`, `write()`      | verstuurt tekst of bytes                                     | soms (zie [5.5.4](#554-functies-die-wachten))           |
| `availableForWrite()`                  | geeft hoeveel bytes er verstuurd kunnen worden zonder wachten | nee                       |
| `flush()`                              | wacht tot alles verstuurd is                                 | ja                         |
| `readBytes()`, `readBytesUntil()`      | leest een aantal bytes                                       | ja, tot een timeout        |
| `readString()`, `readStringUntil()`    | leest tekst als `String` (zie [3.2.5](../3_c_en_cpp/3.2_datatypes.md#325-string-vermijden-char-en-stringh))                         | ja, tot een timeout        |
| `parseInt()`, `parseFloat()`           | leest een getal                                              | ja, tot een timeout        |
| `find()`, `findUntil()`                | zoekt een tekst in de binnenkomende data                     | ja, tot een timeout        |
| `setTimeout()`                         | stelt die timeout in (standaard 1000 ms)                     | nee                        |

## 5.5.3 De belangrijkste functies

Voor bijna alle toepassingen volstaan vijf functies: `begin()`, `print()`,
`println()`, `available()` en `read()`.

### Serial.begin()

`Serial.begin(115200)` start de seriële poort aan 115200 baud, met de
standaardinstelling 8N1 (zie [5.2.7](./5.2_uart.md#527-het-volledige-frame)). Een andere baudrate mag ook, zolang de
Serial Monitor dezelfde gebruikt. Op de ESP32 kan `begin()` ook de
frame-instelling en de pinnen meekrijgen (zie [5.5.5](#555-een-tweede-uart-gebruiken)).

### Serial.print() en Serial.println()

- `print()` stuurt een tekst of de waarde van een variabele door,
  **zonder** regeleinde.
- `println()` doet hetzelfde, en voegt er een regeleinde **aan toe**:
  `\r\n` (zie [5.6.3](./5.6_tekst_en_bytes.md#563-regeleindes)).

De combinatie van beide geeft een duidelijke debugregel: eerst een tekst die
zegt wat er volgt, dan de waarde.

```cpp
Serial.print("pot: ");
Serial.println(pot_value);
```

In de Serial Monitor:

```text
pot: 2048
```

Twee handige extra's:

- Een tweede parameter kiest het talstelsel. Bevat `status_register` de
  waarde 78, dan print `Serial.println(status_register, HEX)` de tekst `4E`,
  en met `BIN` verschijnt `1001110`.
- De ESP32-core heeft ook `Serial.printf()`, met een format string zoals bij
  `snprintf()` (zie [3.4.3](../3_c_en_cpp/3.4_functies.md#343-pass-by-value-en-pass-by-reference)): `Serial.printf("pot: %d\n", pot_value);`. In de
  AVR-core bestaat die functie niet.

> **Let op:** print niet in elke doorloop van `loop()`. `loop()` loopt
> duizenden keren per seconde, en de Serial Monitor loopt dan vol met dezelfde
> regel. Belangrijke meldingen verdwijnen in die stroom, en elke print kost
> bovendien tijd (zie [5.2.8](./5.2_uart.md#528-hoe-snel-is-uart)). Print op specifieke momenten: wanneer een waarde
> verandert, of wanneer er iets gebeurt.

### Serial.available() en Serial.read()

Binnenkomende bytes worden door de core in een **ontvangstbuffer** bewaard tot
het programma ze uitleest:

- `available()` geeft terug hoeveel bytes er in die buffer klaarstaan;
- `read()` haalt de oudste byte uit de buffer.

Daarom staat `read()` altijd achter een controle met `available()`, zoals in
[2.2.2](../2_arduino/2.2_de_serial_monitor.md#222-tekst-naar-het-board-sturen):

```cpp
if (Serial.available() > 0) {
  char received_char = Serial.read();
}
```

Moeten er meerdere tekens tegelijk ingelezen worden, dan is de verleiding groot
om te wachten tot ze er allemaal zijn:

```cpp
const int COMMAND_LENGTH = 10;

char command[COMMAND_LENGTH];

void loop() {
  // blocks: loop() stops here until 10 characters have arrived
  while (Serial.available() < COMMAND_LENGTH) {
  }

  for (int i = 0; i < COMMAND_LENGTH; i++) {
    command[i] = Serial.read();
  }
}
```

Dat werkt, maar zolang de tekens niet binnen zijn, staat het programma stil:
geen knoppen die gelezen worden, geen led die knippert. Beter is om enkel te
lezen als alles er is, en anders meteen verder te gaan:

```cpp
void loop() {
  // only read when all characters have arrived, otherwise continue immediately
  if (Serial.available() >= COMMAND_LENGTH) {
    for (int i = 0; i < COMMAND_LENGTH; i++) {
      command[i] = Serial.read();
    }
  }

  // ... the rest of loop() keeps running
}
```

Commando's met een vaste lengte zijn in de praktijk eerder zeldzaam. Meestal
wordt een regel tekst ingelezen die eindigt op een regeleinde (zie [5.6.4](./5.6_tekst_en_bytes.md#564-van-teken-naar-getal)).

### De ontvangstbuffer is beperkt

De ontvangstbuffer is niet oneindig groot:

- in de AVR-core is ze 64 bytes groot;
- in de ESP32-core 256 bytes, met daarnaast nog een hardwarebuffer (FIFO) van
  128 bytes in de UART zelf. Met `Serial.setRxBufferSize()`, vóór
  `begin()`, kan de buffer groter gemaakt worden.

Leest het programma de buffer niet op tijd uit, dan loopt ze vol en gaan
nieuwe bytes **verloren**. Een GPS-module aan 9600 baud stuurt ongeveer 960
bytes per seconde: een buffer van 256 bytes zit dan na ruim een kwart seconde
vol. Een `delay(500)` in `loop()` volstaat dus al om data te missen.

## 5.5.4 Functies die wachten

Seriële communicatie is traag ten opzichte van de microcontroller (zie
[5.2.8](./5.2_uart.md#528-hoe-snel-is-uart)). Een aantal functies lost dat op door te **wachten**, en dat kan in
beide richtingen.

**Bij het ontvangen** wachten de functies van `Stream` met een timeout:
`readString()`, `readStringUntil()`, `parseInt()`, `parseFloat()`,
`readBytes()`, `find()`, ... Ze wachten tot de verwachte data binnen is, of
tot de timeout verstreken is: standaard 1 seconde, in te stellen met
`setTimeout()`. Tijdens dat wachten staat `loop()` stil. Daarbovenop geeft
`parseInt()` na een timeout `0` terug, waardoor een echte `0` niet te
onderscheiden is van "niets ontvangen". In dit vak worden deze functies dus
niet gebruikt. Inlezen gebeurt teken per teken met `available()` en `read()`
(zie [5.6.4](./5.6_tekst_en_bytes.md#564-van-teken-naar-getal)).

**Bij het zenden** keert `print()` pas terug wanneer de data in de zendbuffer
staat.

- De ESP32-core heeft standaard **geen** zendbuffer in software. De data gaat
  rechtstreeks naar de hardware-FIFO van 128 bytes in de UART. Is er
  onvoldoende plaats, dan wacht `print()` tot er genoeg bytes verstuurd zijn.
- De AVR-core heeft een zendbuffer van 64 bytes, met hetzelfde gevolg zodra
  die vol zit.

Een korte print af en toe is dus geen probleem: die past in de buffer, en
`print()` keert meteen terug. Wie veel print in korte tijd, vertraagt `loop()`
tot het tempo van de UART. Met `availableForWrite()` is op voorhand te zien
hoeveel plaats er nog is. Op de ESP32 kan met `Serial.setTxBufferSize()`,
vóór `begin()`, alsnog een zendbuffer in software voorzien worden.

### Een regel inlezen zonder te wachten

Een regel tekst inlezen, zoals een commando uit de Serial Monitor, lijkt met
`readStringUntil()` eenvoudig:

```cpp
void loop() {
  // blocks: waits for a '\n', or at most 1 s
  String line = Serial.readStringUntil('\n');
}
```

Zolang er geen volledige regel binnen is, staat `loop()` tot een seconde
stil. De **non-blocking** versie verzamelt de tekens zelf in een `char`-array.
Elke doorloop van `loop()` verwerkt enkel de tekens die al in de
ontvangstbuffer staan, en gaat dan meteen verder. Om te tonen dat de rest van
`loop()` blijft lopen, knippert ondertussen een led met `millis()` (zie
[4.4](../4_gpio/4.4_digitale_input.md)):

```cpp
const uint8_t LED_PIN = 17;                     // D10
const unsigned long BLINK_HALF_PERIOD_MS = 250;
const int LINE_BUFFER_SIZE = 32;                // longest line + '\0'

char line_buffer[LINE_BUFFER_SIZE];
int line_length = 0;

unsigned long last_toggle_ms = 0;
bool led_on = false;

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
}

void loop() {
  // handle the characters that have already arrived, without waiting for more
  while (Serial.available() > 0) {
    char received_char = Serial.read();

    if (received_char == '\n') {
      line_buffer[line_length] = '\0';  // line complete: close the C-string
      Serial.print("received: ");
      Serial.println(line_buffer);
      line_length = 0;                  // ready for the next line
    } else if (received_char != '\r' && line_length < LINE_BUFFER_SIZE - 1) {
      line_buffer[line_length] = received_char;
      line_length++;
    }
    // '\r' and characters that do not fit in the buffer are dropped
  }

  // the rest of loop() keeps running, also while a line is still arriving
  if (millis() - last_toggle_ms >= BLINK_HALF_PERIOD_MS) {
    last_toggle_ms = millis();
    led_on = !led_on;
    digitalWrite(LED_PIN, led_on);
  }
}
```

Wat opvalt:

- `line_buffer` en `line_length` zijn **globaal**. Een regel komt vaak
  verspreid over meerdere doorlopen van `loop()` binnen, dus de tekens die al
  ontvangen zijn, moeten bewaard blijven tussen twee doorlopen.
- De `while` wacht niet: zodra de ontvangstbuffer leeg is, geeft `available()`
  `0` terug en stopt de lus, ook als de regel nog niet volledig is.
- De controle `line_length < LINE_BUFFER_SIZE - 1` voorkomt dat er voorbij het
  einde van de array geschreven wordt. De laatste plaats blijft vrij voor de
  `'\0'` (zie [3.2.5](../3_c_en_cpp/3.2_datatypes.md#325-string-vermijden-char-en-stringh)).
- Het `'\r'` dat de Serial Monitor eventueel voor de `'\n'` meestuurt, komt
  niet in de buffer terecht (zie [5.6.3](./5.6_tekst_en_bytes.md#563-regeleindes)).

Wat er met de regel gebeurt, zoals ze omzetten naar een getal, komt aan bod in
[5.6.4](./5.6_tekst_en_bytes.md#564-van-teken-naar-getal).

## 5.5.5 Een tweede UART gebruiken

Voor een externe module wordt een tweede UART gebruikt, zodat UART0 vrij blijft
voor de Serial Monitor. Een typisch voorbeeld is een **GPS-module**. Die
stuurt elke seconde een aantal regels tekst in het **NMEA**-formaat door,
meestal aan 9600 baud. Elke regel begint met `$` en eindigt op `*` gevolgd
door een checksum (zie [5.2.6](./5.2_uart.md#526-foutcontrole-pariteit)):

```text
$GPGGA,123519,4807.038,N,01131.000,E,1,08,0.9,545.4,M,46.9,M,,*47
$GPRMC,123519,A,4807.038,N,01131.000,E,022.4,084.4,230394,003.1,W*6A
```

Het volgende voorbeeld stuurt alles wat de GPS-module verstuurt ongewijzigd
door naar de Serial Monitor:

```cpp
const uint8_t GPS_RX_PIN = 35;             // A3, ESP32 receives here: connect TX of the GPS module
const uint8_t GPS_TX_PIN = 26;             // D3, ESP32 sends here: connect RX of the GPS module
const unsigned long GPS_BAUD_RATE = 9600;  // default baud rate of most GPS modules

HardwareSerial gps_serial(2);  // UART2

void setup() {
  Serial.begin(115200);

  // order of the pins: RX first, then TX
  gps_serial.begin(GPS_BAUD_RATE, SERIAL_8N1, GPS_RX_PIN, GPS_TX_PIN);
  Serial.println("GPS started");
}

void loop() {
  while (gps_serial.available() > 0) {
    char received_char = gps_serial.read();
    Serial.print(received_char);
  }
}
```

Wat opvalt:

- `HardwareSerial gps_serial(2)` maakt een object voor **UART2**, met een
  naam die zegt waarvoor het dient. De core heeft voor UART2 ook al `Serial2`.
  Gebruik in één programma een van beide, niet allebei door elkaar: ze sturen
  dezelfde UART aan.
- De **pinnen** worden vanuit het standpunt van de **ESP32** benoemd:
  `GPS_RX_PIN` is de pin waarop de ESP32 ontvangt, en daar komt de TX van de
  module op (zie [5.2.1](./5.2_uart.md#521-aansluiten)). Een naam als `GPS_RX` zonder meer is dubbelzinnig: is
  dat de RX van de GPS, of de RX voor de GPS? Het commentaar maakt het
  ondubbelzinnig.
- GPIO35 kan enkel input zijn, wat voor een RX-pin volstaat (zie [5.4.4](./5.4_van_usb_naar_uart.md#544-de-uarts-van-de-esp32)).
  Beide pinnen zijn vrij op de Basic GPIO Board.
- De pinnen worden altijd **expliciet** meegegeven. Zonder pinnen kiest de
  core zelf standaardpinnen, en die hangen af van de versie van de core en
  van het board. Ze zijn niet noodzakelijk vrij.
- De GPS stuurt aan 9600 baud, de Serial Monitor ontvangt aan 115200 baud.
  Het doorsturen houdt dus ruim het tempo bij.
- Controleer het **spanningsniveau** van de TX-uitgang van de module. Stuurt
  die 5 V, dan is een spanningsdeler nodig (zie [4.4.3](../4_gpio/4.4_digitale_input.md#443-spanningsniveaus-combineren)).

### Default arguments

De volledige declaratie van `begin()` in `HardwareSerial.h` ziet er zo uit
(ESP32-core, versie 3.3):

```cpp
void begin(
  unsigned long baud, uint32_t config = SERIAL_8N1, int8_t rxPin = -1, int8_t txPin = -1, bool invert = false, unsigned long timeout_ms = 20000UL,
  uint8_t rxfifo_full_thrhd = 120
);
```

De parameters met een `=` hebben een **standaardwaarde** (*default
argument*). Wie ze weglaat, krijgt die waarde. Daarom volstaat
`Serial.begin(115200)`: `config` wordt `SERIAL_8N1`, en de pinnen `-1`, wat
"de standaardpinnen" betekent.

Weglaten kan enkel **achteraan**. Om `rxPin` en `txPin` mee te geven, moet
`config` dus ook ingevuld worden, ook al is `SERIAL_8N1` de standaardwaarde.
Dat is de reden waarom die in het voorbeeld toch expliciet staat.

Default arguments zijn een eigenschap van **C++**. In C, en dus in het ESP-IDF,
bestaan ze niet. Daar wordt met een configuratiestruct gewerkt, zoals in
[5.5.6](#556-onder-de-motorkap-het-esp-idf). Meer uitleg over default arguments staat op
[GeeksforGeeks, Default Arguments in C++](https://www.geeksforgeeks.org/default-arguments-c/).

## 5.5.6 Onder de motorkap: het ESP-IDF

Net zoals `digitalWrite()` een dun laagje is rond `gpio_set_level()` (zie
[2.3.2](../2_arduino/2.3_de_arduino_core.md#232-onder-de-motorkap-digitalwrite-in-de-esp32-core)), is `HardwareSerial` in de ESP32-core een laagje rond de
**UART-driver** van het ESP-IDF. In `cores/esp32/esp32-hal-uart.c` is te
zien welke functies achter de schermen gebruikt worden:

| Arduino           | ESP-IDF                                         |
| ----------------- | ----------------------------------------------- |
| `begin()`         | `uart_driver_install()`, `uart_param_config()`  |
| `write()`, `print()` | `uart_write_bytes()`                         |
| `available()`     | `uart_get_buffered_data_len()`                  |
| `read()`          | `uart_read_bytes()`                             |

In het ESP-IDF is UART0 standaard de **console**: alles wat met `printf()` of
de logfuncties uit [2.3.2](../2_arduino/2.3_de_arduino_core.md#232-onder-de-motorkap-digitalwrite-in-de-esp32-core) geprint wordt, gaat aan 115200 baud naar UART0, en
dus via de bridge naar de computer. Een `begin()` is daarvoor niet nodig. De
rol van de Serial Monitor wordt overgenomen door `idf.py monitor`.

Het GPS-voorbeeld uit [5.5.5](#555-een-tweede-uart-gebruiken) rechtstreeks in het ESP-IDF:

```c
#include <stdio.h>
#include "driver/uart.h"
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"

#define GPS_UART_NUM UART_NUM_2
#define GPS_RX_GPIO 35         // A3, ESP32 receives here: connect TX of the GPS module
#define GPS_TX_GPIO 26         // D3, ESP32 sends here: connect RX of the GPS module
#define GPS_BAUD_RATE 9600
#define RX_BUFFER_SIZE 256     // ring buffer of the driver, must be larger than the 128 byte FIFO
#define READ_TIMEOUT_MS 100

void app_main(void) {
  uart_config_t uart_config = {
    .baud_rate = GPS_BAUD_RATE,
    .data_bits = UART_DATA_8_BITS,
    .parity = UART_PARITY_DISABLE,
    .stop_bits = UART_STOP_BITS_1,
    .flow_ctrl = UART_HW_FLOWCTRL_DISABLE,
    .source_clk = UART_SCLK_DEFAULT,
  };
  ESP_ERROR_CHECK(uart_driver_install(GPS_UART_NUM, RX_BUFFER_SIZE, 0, 0, NULL, 0));
  ESP_ERROR_CHECK(uart_param_config(GPS_UART_NUM, &uart_config));

  // order of the pins: TX first, then RX
  ESP_ERROR_CHECK(uart_set_pin(GPS_UART_NUM, GPS_TX_GPIO, GPS_RX_GPIO, UART_PIN_NO_CHANGE, UART_PIN_NO_CHANGE));

  uint8_t data[64];

  while (1) {
    // waits until 64 bytes have arrived, or at most READ_TIMEOUT_MS
    int length = uart_read_bytes(GPS_UART_NUM, data, sizeof(data), pdMS_TO_TICKS(READ_TIMEOUT_MS));

    if (length > 0) {
      printf("%.*s", length, (const char *)data);  // forward to the console on UART0
    }
  }
}
```

Wat opvalt:

- De afspraken uit [5.2.2](./5.2_uart.md#522-vier-afspraken) staan expliciet in een configuratiestruct: baudrate,
  databits, pariteit en stopbits. Wat in Arduino verborgen zit in
  `SERIAL_8N1`, is hier volledig zichtbaar.
- `uart_set_pin()` verwacht **eerst TX, dan RX**. `begin()` in de Arduino core
  verwacht net omgekeerd eerst RX. Twee functies voor hetzelfde, met een
  andere volgorde: controleer bij elke functie de declaratie, en vertrouw
  niet op de volgorde van een andere functie.
- `uart_read_bytes()` wacht, net als de functies uit [5.5.4](#554-functies-die-wachten), maar dan met een
  timeout die in de code staat. In het ESP-IDF is wachten minder erg dan in
  een Arduino-`loop()`: terwijl een taak wacht, kan FreeRTOS andere taken
  uitvoeren.
