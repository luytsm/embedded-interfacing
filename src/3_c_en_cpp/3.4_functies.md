# 3.4 Functies

Een **functie** groepeert een stuk code onder een naam, zodat het op
meerdere plaatsen hergebruikt kan worden. Elke sketch bevat er al minstens
twee: `setup()` en `loop()`. Ook `digitalWrite()` en `delay()` zijn gewone
functies (zie 3.1).

Functies maken code niet enkel korter, maar vooral **leesbaarder**: een
goedgekozen naam als `blink_led()` zegt meer dan vijf regels code.

## 3.4.1 Opbouw van een functie

```cpp
int add(int a, int b) {
  return a + b;
}
```

| Deel             | Betekenis                                                                 |
| ---------------- | ------------------------------------------------------------------------- |
| `int`            | het **return type**: het datatype van de waarde die de functie teruggeeft |
| `add`            | de **naam** van de functie                                                |
| `(int a, int b)` | de **parameters**: de waarden die de functie meekrijgt, elk met een type  |
| `{ ... }`        | de **body**: de code die uitgevoerd wordt                                 |
| `return`         | verlaat de functie en geeft een waarde terug                              |

Een functie die niets teruggeeft, krijgt het return type **`void`**. Een
functie zonder parameters krijgt lege haakjes:

```cpp
void blink_led(int pin, int duration_ms) {
  digitalWrite(pin, HIGH);
  delay(duration_ms);
  digitalWrite(pin, LOW);
  delay(duration_ms);
}

void setup() {
  pinMode(LED_BUILTIN, OUTPUT);
}

void loop() {
  blink_led(LED_BUILTIN, 200);
  blink_led(LED_BUILTIN, 1000);
}
```

`return` mag ook in een `void`-functie voorkomen, zonder waarde, om de
functie vroegtijdig te verlaten. Dat is precies wat een guard clause doet
(zie 3.3.1).

## 3.4.2 Declaratie en definitie

In C en C++ moet een functie **gekend zijn vóór ze gebruikt wordt**. De
compiler leest de code van boven naar onder. Wordt een functie aangeroepen
die pas verderop staat, dan volgt een foutmelding.

Daarom wordt onderscheid gemaakt tussen:

- de **declaratie** (ook **prototype** genoemd): enkel de "handtekening" van
  de functie, afgesloten met een `;`
- de **definitie**: de volledige functie, met body

Het volgende voorbeeld leest elke seconde een LM35-temperatuursensor uit op
een Nano:

```cpp
float read_temperature(int pin);          // declaration (prototype)

void setup() {
  Serial.begin(115200);
}

void loop() {
  float temperature = read_temperature(A0);   // OK: read_temperature() is known
  Serial.println(temperature);
  delay(1000);
}

float read_temperature(int pin) {         // definition
  int raw = analogRead(pin);
  float voltage = raw * 5.0 / 1023.0;     // 10-bit ADC, 5 V reference
  return voltage * 100.0;                 // LM35: 10 mV per degree Celsius
}
```

In grotere projecten staan de declaraties in een **header-bestand** (`.h`) en
de definities in een `.c`- of `.cpp`-bestand. Zo kan de sketch de functie
gebruiken door enkel de header te `#include`'n:

```cpp
// temperature_sensor.h
float read_temperature(int pin);
```

```cpp
// temperature_sensor.cpp
#include <Arduino.h>
#include "temperature_sensor.h"

float read_temperature(int pin) {
  int raw = analogRead(pin);
  float voltage = raw * 5.0 / 1023.0;
  return voltage * 100.0;
}
```

```cpp
// main sketch (.ino)
#include "temperature_sensor.h"
```

> **Let op:** de Arduino IDE genereert voor een `.ino`-bestand automatisch
> de prototypes van alle functies. Daardoor werkt het eerste voorbeeld ook
> zonder de declaratie bovenaan. In een gewoon `.c`- of `.cpp`-bestand, en
> dus ook in het ESP-IDF, gebeurt dat **niet**. Wie code overzet van een
> sketch naar een ander bestand, loopt hier vaak tegenaan.

## 3.4.3 Pass by value en pass by reference

Een functie kan met `return` slechts **één waarde** teruggeven. In embedded
code is dat vaak te weinig: bij het uitlezen van een sensor is naast de
meetwaarde ook belangrijk of de meting **gelukt** is. Een losgekomen draad
geeft immers ook een getal, alleen een zinloos.

Een voor de hand liggende poging is het meetresultaat wegschrijven in een
parameter. Dat werkt niet: standaard krijgt een functie een **kopie** van de
meegegeven waarde (*pass by value*). Aanpassingen binnen de functie hebben
geen effect op de originele variabele:

```cpp
void read_sensor(int pin, int result) {
  result = analogRead(pin);       // only changes the copy
}

void loop() {
  int measurement = 0;
  read_sensor(A0, measurement);   // measurement is still 0
}
```

Moet de functie de originele variabele wel aanpassen, dan wordt het
**adres** van die variabele meegegeven. In C gebeurt dat met een
**pointer** (`*`), in C++ kan het ook met een **reference** (`&`). De
return-waarde blijft zo vrij om aan te geven of de meting gelukt is:

```cpp
// C: pointer
bool read_sensor_ptr(int pin, int *result) {
  int raw = analogRead(pin);
  if (raw == 0 || raw == 1023) {
    return false;                 // at the edge of the range: probably a broken wire
  }
  *result = raw;                  // write the measurement into the original variable
  return true;
}

// C++: reference
bool read_sensor_ref(int pin, int &result) {
  int raw = analogRead(pin);
  if (raw == 0 || raw == 1023) {
    return false;
  }
  result = raw;
  return true;
}

void loop() {
  int measurement;

  if (read_sensor_ptr(A0, &measurement)) {
    Serial.println(measurement);
  } else {
    Serial.println("sensor error");
  }
  delay(1000);
}
```

Een reference is eenvoudiger in gebruik, maar bestaat enkel in C++. Omdat het
ESP-IDF in C geschreven is, komen pointers daar veel vaker voor.

> **Strikt genomen** kent C helemaal geen pass by reference: in C wordt
> **alles by value** doorgegeven. Wat in C vaak "by reference" genoemd wordt,
> is in feite een **pointer die by value doorgegeven wordt**. De functie
> krijgt een kopie van het adres. Via die kopie kan de originele variabele
> aangepast worden, maar de pointer zelf aanpassen heeft geen effect buiten
> de functie:
>
> ```c
> void read_sensor_wrong(int *result) {
>   int raw = analogRead(A0);
>   result = &raw;                  // only changes the copy of the address
> }
>
> void read_sensor_right(int *result) {
>   *result = analogRead(A0);       // writes into the original variable
> }
> ```
>
> Echte pass by reference bestaat pas in C++, met de `&` in de parameterlijst.

### Status teruggeven, resultaat via een pointer

In `read_sensor_ptr()` hierboven geeft de return-waarde de **status** (gelukt of
niet), en wordt het **resultaat** via een pointer weggeschreven. Dat patroon
is in C zeer gebruikelijk. Waarom wordt het resultaat dan niet gewoon
gereturned?

Soms kan dat wel, met een speciale waarde die een fout aanduidt. `analogRead()`
geeft op een Nano een waarde van 0 tot 1023, dus `-1` kan nooit een echte
meting zijn en is bruikbaar als foutcode. Dat werkt enkel zolang er waarden
bestaan die nooit als geldig resultaat voorkomen. Bij een temperatuur is dat
niet het geval: `-1.0` °C is een perfect geldige meting, net als `0`. Er
blijft geen enkel getal over om een fout aan te geven. Bovendien kent C geen
*exceptions* zoals C++, Java of Python, dus een fout moet via een gewone
waarde teruggegeven worden.

Door de rollen te splitsen, is elk deel eenduidig:

- de **return-waarde** zegt enkel of het gelukt is
- de **pointer** is de plaats waar het resultaat weggeschreven wordt, en die
  wordt enkel ingevuld als het gelukt is

Dit heeft nog twee voordelen. Een functie kan zo **meerdere resultaten**
wegschrijven, bijvoorbeeld temperatuur én luchtvochtigheid van één sensor.
En in plaats van een `bool` kan de return-waarde een **foutcode** zijn, die
ook zegt *wat* er misliep.

```cpp
bool read_climate(float *temperature, float *humidity);

void loop() {
  float temperature;
  float humidity;

  if (!read_climate(&temperature, &humidity)) {
    Serial.println("sensor error");
    return;
  }
  Serial.println(temperature);
  Serial.println(humidity);
}
```

### Use case: esp_err_t in het ESP-IDF

Het ESP-IDF past dit patroon consequent toe. Bijna elke functie geeft een
**`esp_err_t`** terug: `ESP_OK` (0) bij succes, anders een foutcode. Het
resultaat, als er een is, komt via een pointer. Zo leest `nvs_get_i32()`
een waarde uit het flashgeheugen (NVS, *non-volatile storage*), bijvoorbeeld
hoe vaak het board al opgestart is:

```c
int32_t boot_count = 0;
esp_err_t err = nvs_get_i32(nvs_handle, "boot_count", &boot_count);

switch (err) {
  case ESP_OK:
    // boot_count now holds the stored value
    break;
  case ESP_ERR_NVS_NOT_FOUND:
    // first boot: nothing stored yet, boot_count stays 0
    break;
  default:
    ESP_LOGE("app", "reading NVS failed: %s", esp_err_to_name(err));
    break;
}
```

Elke `int32_t` kan hier een geldige opgeslagen waarde zijn, dus returnen
zou niet werken. De foutcode maakt bovendien een onderscheid tussen "nog
niets opgeslagen" (bij de eerste opstart perfect normaal) en een echte fout.

Omdat het hele framework hetzelfde patroon volgt, wordt foutafhandeling
overal op dezelfde manier geschreven. `esp_err_to_name()` zet elke foutcode
om naar leesbare tekst, en de macro `ESP_ERROR_CHECK()` stopt het programma
met een duidelijke melding wanneer een aanroep die nooit mag mislukken toch
een fout teruggeeft:

```c
ESP_ERROR_CHECK(nvs_flash_init());
```

### Arrays als parameter

**Arrays** vormen een uitzondering: een array wordt nooit gekopieerd. De
functie krijgt altijd een pointer naar het eerste element. De functie weet
daardoor ook niet hoe groot de array is, dus de lengte wordt meestal als
extra parameter meegegeven. 

### char buff[] tegenover const char *

Bij tekst duikt het verschil tussen een array en een pointer het vaakst op.
Beide declaraties lijken op elkaar, maar doen iets anders:

```cpp
char message_buffer[32];                  // 32 bytes of writable memory
const char *error_text = "sensor error";  // pointer to a fixed text
```

- `char message_buffer[32]` reserveert **32 bytes geheugen** waarin
  geschreven mag worden.
- `const char *error_text` is enkel een **pointer**: een adres dat naar een
  vaste tekst verwijst. Die tekst (een *string literal*) plaatst de compiler
  zelf ergens in het geheugen, en die mag niet aangepast worden. Op een
  ESP32 staat zo'n tekst in flash, en een poging om erin te schrijven laat
  het board crashen. Zonder `const` geeft de compiler een waarschuwing.

|                                    | `char buff[32]`         | `const char *text`                                           |
| ---------------------------------- | ----------------------- | ------------------------------------------------------------ |
| Wat is het?                        | een array van 32 tekens | een adres dat naar tekst wijst                               |
| Schrijven in de inhoud             | ja                      | nee                                                          |
| Naar een andere tekst laten wijzen | nee                     | ja                                                           |
| `sizeof`                           | 32                      | grootte van een pointer: 2 bytes op een Nano, 4 op een ESP32 |

Als **parameter** verdwijnt het verschil: `void f(char buff[])` en
`void f(char *buff)` zijn voor de compiler identiek, want een array wordt
altijd als pointer doorgegeven. Binnen de functie geeft `sizeof(buff)` dus
de grootte van een pointer en niet die van de array. Daarom wordt de grootte
van een buffer altijd apart meegegeven:

```cpp
void format_measurement(char *buffer, size_t buffer_size, int measurement) {
  snprintf(buffer, buffer_size, "A0: %d", measurement);
}

void log_status(const char *text) {
  Serial.print("status: ");
  Serial.println(text);
}

void loop() {
  char line[32];

  // sizeof works here: line is still an array in this function
  format_measurement(line, sizeof(line), analogRead(A0));
  Serial.println(line);

  log_status("ok");
  delay(1000);
}
```

`format_measurement()` schrijft een meetresultaat weg en heeft dus een
buffer nodig. `log_status()` leest enkel een tekst en krijgt daarom een
`const char *`.

> **Vuistregel:** gebruik `char buff[N]` wanneer er een buffer nodig is om
> in te schrijven, zoals bij `snprintf()` of het inlezen van seriële data.
> Gebruik `const char *` wanneer er enkel naar een vaste tekst verwezen
> wordt.

## 3.4.4 Goede gewoontes

- Een functie doet **één ding**, en de naam zegt wat. Past de beschrijving
  niet in één korte zin, dan is de functie vermoedelijk te groot.
- Gebruik een werkwoord in de naam: `read_temperature()`, `set_motor_speed()`.
- Houd het aantal parameters beperkt. Veel parameters wijzen vaak op een
  functie die te veel doet.
- Vermijd globale variabelen waar een parameter of return-waarde volstaat.
  Een functie die enkel met haar parameters werkt, is eenvoudiger te testen
  en te hergebruiken.
